# План реализации по шагам

> Дополнение к `about.md`, §15. Каждый из 11 этапов разбит на последовательные шаги.
> Правило: не переходить к следующему шагу, пока не получен **ожидаемый результат** предыдущего — так вы всегда сможете локализовать баг в том, что делали последние 30 минут, а не искать его по всему кластеру.

---

## Этап 1. Workflow Engine (соло, без кластера)

Цель этапа: получить работающий DAG-движок на одной машине, без сети и без Raft — это ядро, вокруг которого строится всё остальное.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 1.1 | Создать скелет монорепы: `go.mod`, пустые `common/domain`, `cmd/orc` | `go build ./...` проходит без ошибок на пустом каркасе |
| 1.2 | Реализовать структуры из ТЗ §2 в `common/domain`: `Task`, `Workflow`, `TaskStatus`, `WorkflowStatus` | Юнит-тест создаёт `Workflow` с 3 задачами и компилируется |
| 1.3 | Реализовать валидацию DAG (§4): проверка существования `DependsOn`, поиск циклов через DFS с тремя цветами | Тест на графе с циклом возвращает ошибку; тест на валидном графе — `nil` |
| 1.4 | Реализовать `WorkflowEngine.SubmitWorkflow` поверх **in-memory** map (без FSM/Raft — просто `map[WorkflowID]*Workflow` с мьютексом) | `SubmitWorkflow` принимает workflow, возвращает `WorkflowID`, кладёт в память |
| 1.5 | Реализовать `recomputeReadyTasks` и `OnTaskCompleted` | В тесте: вручную вызвать `OnTaskCompleted` для задачи `build` → задача `test` переходит в `READY` |
| 1.6 | Добавить логирование переходов статусов (`log/slog`, пока просто в stdout) | Демо-программа с DAG `build → test → deploy` печатает переходы `PENDING → READY → SUCCEEDED` в правильном топологическом порядке |

**Definition of Done этапа:** можно из кода создать `Workflow` с зависимостями и увидеть корректный порядок обработки в логах — без единого байта, ушедшего по сети.

## Этап 2. Job Scheduler + один воркер

Цель этапа: задачи из этапа 1 реально исполняются — но пока на одном воркере, без отказоустойчивости.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 2.1 | Написать `docs/proto/worker.proto` (`ClusterService`: `Register`, `Heartbeat`, `ReportResult` — сервер control-plane; `WorkerRPC`: `Dispatch` — сервер воркер) и сгенерировать код в `common/api/workerpb` | `protoc`/`buf generate` проходит без ошибок, пакет импортируется |
| 2.2 | Поднять `cmd/worker/main.go`: gRPC-сервер, реализующий `Dispatch` заглушкой (просто логирует полученную задачу) | `go run ./cmd/worker` стартует, `grpcurl` до `Dispatch` получает ответ |
| 2.3 | Реализовать `ShellExecutor` (§6.4) | Юнит-тест: `Execute(ctx, {cmd: "echo hello"})` возвращает `TaskResult{ExitCode: 0, Stdout: "hello\n"}` |
| 2.4 | Реализовать `WorkerRegistry` (§6.1, пока без health-check) и `Scheduler.assignOnce` + `SelectWorker` (§5) в самом простом виде — единственный захардкоженный воркер | Задача в статусе `READY` подхватывается планировщиком и логируется как назначенная |
| 2.5 | Реализовать `GRPCWorkerClient` (§6.1) и подключить его к `Scheduler` — теперь `commitAssignment` реально вызывает `WorkerRPC.Dispatch` по сети, а не логирует | Отправка workflow из 1.6 приводит к реальному запуску процесса на воркере и получению результата назад |
| 2.6 | Прогнать полный DAG `build → test → deploy` из этапа 1 через реального воркера | Все 3 задачи выполняются по очереди (с учётом зависимостей), workflow переходит в `SUCCEEDED` |

**Definition of Done этапа:** реальный `go build`/`go test`/`deploy.sh` выполняются на воркере, статусы обновляются по факту исполнения.

## Этап 3. Несколько воркеров + Orchestration

Цель этапа: кластер воркеров переживает падение отдельного воркера.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 3.1 | Написать `docs/proto/orchestrator.proto` (`OrchestratorAPI`: `SubmitWorkflow`, `GetWorkflow`, §10.1), реализовать сервер на control-plane и минимальный `orc submit`/`orc get` (пока прямой gRPC-клиент к единственному узлу, без `LeaderAwareClient` — он появится в этапе 5) | `orc submit workflow.yaml` реально создаёт workflow через API, а не через тестовый код напрямую |
| 3.2 | Реализовать `WorkerRegistry.Register` (§6.1) | Два запущенных процесса воркера регистрируются → в реестре 2 записи с разными `WorkerID` |
| 3.3 | Реализовать периодический `Heartbeat` с обеих сторон | В логах control-plane видно регулярные heartbeat от обоих воркеров, `LastHeartbeat` обновляется |
| 3.4 | Реализовать health-check через `pkg/retryqueue` (dead man's switch): `ALIVE → DEAD` по таймауту heartbeat (§6.3) | Убить один воркер (`kill -9`) → через grace period control-plane помечает его `DEAD` в логах |
| 3.5 | Реализовать переназначение задач с упавшего воркера: на этой стадии (Raft ещё нет, до этапа 5) обратный индекс `tasksByWorker map[string][]string` — обычное поле прямо в `WorkflowEngine`, под тем же `mutex`, что и `workflows`; `TasksAssignedTo`/`ReassignTask` читают/пишут его напрямую, in-memory, без FSM | Убить воркер во время выполнения `RUNNING`-задачи → задача возвращается в `READY`, переназначается второму воркеру, завершается там |
| 3.6 | Улучшить `SelectWorker` до least-loaded (по `RunningTasks/Capacity`) | Workflow с 6 параллельными задачами при 2 воркерах распределяется примерно поровну (3/3), а не всё на первый |
| 3.7 | Перевести диспетчеризацию задач на воркере на `pkg/executorregistry.Registry` (§6.4) вместо `switch`/`if` по типу; реализовать `HTTPExecutor` вторым исполнителем | Воркер при старте логирует список зарегистрированных типов (`shell`, `http`); оба типа задач реально исполняются одним и тем же воркером |
| 3.8 | Добавить `Capabilities` в `WorkerNode`/`RegisterRequest` (§2, §6.2), фильтрацию по ним в `SelectWorker` **до** остальных алгоритмов (§5.1, шаг 0) | Воркер, запущенный с `capabilities: [http]`, никогда не получает `shell`-задачу, даже если он единственный `ALIVE` |
| 3.9 | Поднять два раздельных пула воркеров одним и тем же бинарником, с разным конфигом (`worker-shell-pool.yaml`/`worker-http-pool.yaml`, §5.1) | `shell`-задачи и `http`-задачи распределяются по своим пулам независимо; можно скейлить/убивать `http`-пул, не трогая `shell`-пул |
| 3.10 | Реализовать `WorkflowEngine.CancelWorkflow` (§4.3), `WorkerRPC.CancelTask` (§6.2) и отслеживание `context.CancelFunc` исполняющихся задач на воркере (§6.4); добавить проверку терминального статуса в начале `OnTaskCompleted` (идемпотентность против гонки с отменой) | `orc submit` долгий `shell`-workflow → `orc cancel workflow <id>` во время `RUNNING`-задачи → процесс на воркере реально убит (не просто помечен отменённым в БД), `orc get workflow <id>` показывает `CANCELLED` |
| 3.11 | Реализовать `ReverseDeps`/`cancelDownstream`/`finalizeWorkflowIfDone` (§4.1, §4.2) — каскадная отмена зависимых задач при падении/отмене одной задачи; `WorkflowEngine.CancelTask` + `OrchestratorAPI.CancelTask` (§4.4, `orc cancel task`) | В графе `build → test → deploy` уронить `test` (исчерпать retries) → `deploy` уходит в `CANCELLED` сам, без ручного вмешательства; независимая ветка `lintA → lintB` в том же workflow продолжает идти как ни в чём не бывало |

**Definition of Done этапа:** `orc submit workflow.yaml` → можно вырубить любой воркер в любой момент — workflow всё равно доходит до `SUCCEEDED` на оставшихся; система умеет исполнять как минимум два разных типа задач на разных, независимо масштабируемых пулах воркеров одного бинарника; workflow целиком или отдельную задачу можно отменить в любой момент, и это реально останавливает исполнение (а не только статус в базе), с корректным каскадом на зависимые задачи и без остановки независимых веток графа.

## Этап 4. Raft: leader election

Цель этапа: control-plane перестаёт быть одной точкой отказа — кластер сам выбирает лидера.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 4.1 | Создать `pkg/raft` со структурами `NodeState`, `PersistentState`, `VolatileState` (§3.3), список пиров в конфиге | Компилируется, юнит-тест создаёт 3 объекта `Node` в памяти |
| 4.2 | Реализовать `RequestVote` + election timeout (случайный таймер 150–300мс) на in-memory транспорте (без сети, вызовы напрямую между объектами в тесте) | Тест с 3 узлами: ровно один становится `Leader`, остальные — `Follower` |
| 4.3 | Завернуть RPC в реальный gRPC-транспорт, поднять 3 отдельных процесса (`docker-compose`) | В логах всех трёх процессов согласованно виден один и тот же `LeaderID` |
| 4.4 | Добавить CLI-команду `orc cluster status` | Команда показывает роль (`Leader`/`Follower`) и `Term` каждого узла |
| 4.5 | Chaos-тест: `kill -9` лидеру | Новый лидер избирается за 1–2 election timeout (обычно < 1 секунды), видно через `orc cluster status` |
| 4.6 | Прогнать 4.5 пятьдесят раз подряд (скриптом) | Ни разу кластер не зависает без лидера дольше нескольких секунд (проверка на split-vote и корректность рандомизации таймера) |

**Definition of Done этапа:** можно убивать лидера сколько угодно раз — кластер каждый раз сам восстанавливает единственного лидера.

## Этап 5. Raft: log replication + интеграция FSM

Цель этапа: решения планировщика реплицируются и переживают падение лидера без потери и без дублирования.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 5.1 | Реализовать `AppendEntries` в режиме heartbeat (пустые `Entries`) | Follower перестаёт запускать выборы, пока получает heartbeat от лидера |
| 5.2 | Реализовать полноценную репликацию записей + продвижение `CommitIndex` по quorum | Интеграционный тест: лидер добавляет запись → все 3 узла подтверждают её наличие в применённом состоянии |
| 5.3 | Реализовать `raftfsm.OrchestratorFSM.Apply` для всех типов команд из §3.5. Заодно перенести `tasksByWorker` из плоского поля `WorkflowEngine` (этап 3.5) внутрь FSM — контракт `TasksAssignedTo`/`ReassignTask` наружу не меняется, меняется только внутреннее хранение | Юнит-тест на детерминизм: один и тот же `LogEntry` применённый дважды к двум чистым FSM даёт идентичное состояние |
| 5.4 | Переключить `WorkflowEngine.SubmitWorkflow` и `Scheduler.Assign` — теперь пишут не в память напрямую, а через Raft-лог | Отправка запроса на follower возвращает ошибку "not leader" с адресом текущего лидера, а не тихо теряется |
| 5.5 | Chaos-тест: убить лидера прямо посреди выполнения workflow из 3+ задач | После failover workflow всё равно доходит до `SUCCEEDED`; ни одна задача не выполнена дважды и ни одна не потеряна (проверить через лог выполнения) |
| 5.6 | Реализовать `common/client.LeaderAwareClient` (§10.2): перехват "not leader" + `LeaderHint`, ретрай на реальном лидере; переключить `orc` на него | `orc submit` продолжает работать без единой ручной правки адреса, даже если вы `kill -9` лидера прямо во время выполнения команды |

**Definition of Done этапа:** весь функционал этапов 1–3 теперь идёт через консенсус — падение лидера не приводит ни к потере, ни к дублированию состояния.

## Этап 6. Persistence

Цель этапа: узел переживает полный рестарт процесса/машины без потери состояния.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 6.1 | Реализовать обёртку над `bbolt` в `pkg/boltstore` (Put/Get/Iterate) | Юнит-тест: запись и чтение ключа round-trip корректно |
| 6.2 | Персистить Raft-лог и метаданные (`CurrentTerm`, `VotedFor`) на диск с `fsync` до ответа `Success: true` | `kill -9` узла → рестарт → в логах видно, что `Term`/`VotedFor`/лог восстановлены, узел не начинает с нуля |
| 6.3 | Реализовать `Snapshot`/`Restore` для FSM (сериализация карты workflows/workers) | После рестарта `orc get workflow <id>` возвращает тот же статус, что был до падения |
| 6.4 | Реализовать компакцию лога при превышении порога (например 10 000 записей) | Метрика `raft_log_length` перестаёт расти бесконечно, стабилизируется около порога |
| 6.5 | Реализовать `InstallSnapshot` для сильно отставшего узла | Добавить в кластер узел, простоявший выключенным долго (лог уже обрезан) → он догоняет через snapshot, а не через миллион `AppendEntries` |

**Definition of Done этапа:** можно вырубить питание любому узлу, включить обратно — он полностью восстанавливается сам, без ручного вмешательства.

## Этап 7. Observability

Цель этапа: по системе видно, что происходит, без `fmt.Println` и логов вручную по трём терминалам.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 7.1 | Перевести все логи на структурированный `log/slog` с обязательными полями (`node_id`, `component`, `trace_id`) | Логи — валидный JSON, можно фильтровать по `component=raft` через `jq` |
| 7.2 | Поднять `/metrics` (Prometheus) на каждом узле, реализовать метрики из §8.2 | `curl localhost:PORT/metrics` отдаёт `raft_current_term`, `scheduler_ready_queue_length` и т.д. |
| 7.3 | Собрать `docker-compose` стек: 3 control-plane + Prometheus + Grafana | Дашборд в Grafana показывает `raft_state` по всем трём узлам одновременно |
| 7.4 | Прокинуть `trace_id` через весь путь: API → Raft-команда → dispatch → результат (в metadata gRPC-вызовов) | В Jaeger по одному `trace_id` виден полный путь одной задачи через весь кластер |
| 7.5 | Написать простой нагрузочный генератор (свой на Go или `k6`), отправляющий N workflow/сек | Во время прогона метрики в Grafana меняются в реальном времени (не просто нули) |

**Definition of Done этапа:** любую проблему в кластере можно диагностировать через дашборд + Jaeger, не перечитывая логи руками.

## Этап 8. Multi-tenancy

Цель этапа: систему можно безопасно шарить между несколькими независимыми командами.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 8.1 | Реализовать `Tenant`, хранение `APIKeyHash`, интерсептор `TenantAuthMiddleware` (§9.2) | Юнит-тест: два разных API-ключа маппятся на два разных `TenantID` |
| 8.2 | Проставлять `TenantID` в `Workflow` при `SubmitWorkflow` из контекста аутентификации | Запрос без валидного ключа получает `Unauthenticated`, а не создаёт workflow |
| 8.3 | Скоупить чтение по тенанту (`GetWorkflow` не отдаёт чужие данные) | Интеграционный тест: тенант A не может получить `WorkflowID` тенанта B (`NotFound`/`PermissionDenied`) |
| 8.4 | Партиционировать `ReadyQueue` по тенанту + round-robin между тенантами в `Scheduler.Assign` | Залить очередь 1000 задачами тенанта A и 1 задачей тенанта B → задача B выполняется без аномального ожидания, а не после всех 1000 |
| 8.5 | Реализовать проверку `ResourceQuota` перед `SubmitWorkflow` | Превышение `MaxConcurrentWorkflows` возвращает `ResourceExhausted`, а не бесконечно висящий запрос |

**Definition of Done этапа:** два независимых API-ключа видят только свои данные, и ни один тенант не может "убить" систему для остальных.

## Этап 10. API Gateway & CLI

Цель этапа: у системы появляется полноценный внешний интерфейс — не только для вас как разработчика (`orc`), но и для фронтенда, который не умеет в сырой gRPC.

| Шаг | Что делать | Ожидаемый результат |
|---|---|---|
| 10.1 | Расширить `orc` до полного набора команд из §10.3 (`watch`, `cluster status`, `worker list`), используя уже готовый `LeaderAwareClient` из этапа 5.6 | `orc cluster status` показывает роль и `Term` каждого узла; `orc watch workflow <id>` стримит живые события через `StreamWorkflowEvents` |
| 10.2 | Поднять `cmd/apigateway/main.go` с `grpc-gateway` поверх `docs/proto/orchestrator.proto` (§10.4) | `curl -X POST localhost:8080/v1/workflows -d @workflow.json` создаёт workflow через REST, без единого байта gRPC на стороне клиента |
| 10.3 | Реализовать SSE-эндпоинт в `infrastructure/apigateway/sse`, транслирующий `StreamWorkflowEvents` | Браузер через `EventSource('/v1/workflows/{id}/events')` получает живые обновления статуса без polling |
| 10.4 | Добавить rate limiting входящих запросов в `infrastructure/apigateway/ratelimit` | Шквал запросов с одного IP получает `429 Too Many Requests` от Gateway, не долетая до control-plane |
| 10.5 | Убедиться, что `TenantAuthMiddleware` (§9.2) по-прежнему обязателен на control-plane, а не только на Gateway | Прямой gRPC-запрос в control-plane в обход Gateway без API-ключа всё равно получает `Unauthenticated` |

**Definition of Done этапа:** фронтенд может создать workflow и подписаться на его статус через обычный HTTP/SSE, ничего не зная про gRPC или про то, кто из трёх control-plane узлов сейчас лидер.

## Этап 11. Universal Task Engine

Цель этапа: движок перестаёт быть "CI/CD-пайплайнером" и может описать в YAML произвольный процесс — закупки, согласования, любой процесс с человеком в контуре — не трогая ядро.

**Definition of Done этапа:** можно описать в YAML процесс из другой предметной области (например, согласование закупки) и запустить его на том же движке, что и CI/CD-пайплайн из этапов 1–3 — без изменений в ядре, только новые `Executor`'ы и YAML.

---

## Как этим пользоваться

- Не начинайте следующий этап, пока не выполнен **Definition of Done** предыдущего — большинство "непонятных" багов в распределённых системах на самом деле являются недособранным предыдущим слоем.
- Каждый шаг внутри этапа старайтесь коммитить отдельно — так откат до последнего рабочего состояния занимает секунды, а не часы разбора.
- Если застряли на каком-то шаге дольше, чем на 2-3 предыдущих вместе взятых — это сигнал, что стоит уменьшить шаг ещё сильнее, а не "просто доделать".
